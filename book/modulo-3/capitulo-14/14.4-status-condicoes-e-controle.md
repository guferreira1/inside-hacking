# 14.4 — Terminar não é necessariamente dar certo

[← Seção 14.3](14.3-fluxos-redirecionamentos-e-pipelines.md) · [Próxima seção →](14.5-scripts-contexto-e-repetibilidade.md)

Uma automação precisa tomar decisões sem perguntar a alguém diante da tela. Para isso, uma etapa deve comunicar um resultado de maneira que outra consiga interpretar.

O problema aparece quando usamos como critério a última frase impressa, a presença de um arquivo ou apenas o fato de o terminal ter devolvido o prompt.

## O código precisa ser lido enquanto ainda é o código certo

Nos exemplos Bash, zero indica sucesso; valores diferentes de zero indicam outros resultados conforme o contrato do comando. `$?` contém o status do último comando relevante concluído. Um novo comando normalmente substitui esse valor. [S29](referencias.md#s29)

Veja:

```bash
false
estado=$?
printf 'estado=%s\n' "$estado"
```

`false` é um comando feito para retornar um status de insucesso. Guardamos imediatamente o valor antes de executar `printf`. O exemplo produz `estado=1` no Bash utilizado nos testes.

Se escrevêssemos uma mensagem antes de consultar `$?`, poderíamos estar examinando o sucesso da própria mensagem, não o resultado que queríamos investigar.

Essa diferença reaparece em sistemas maiores: “o wrapper terminou” e “a operação interna deu certo” não são a mesma informação.

## Nem todo resultado diferente de zero é a mesma falha

No GNU grep, o resultado normal é zero quando há linha selecionada, um quando não há correspondência e dois quando ocorre erro. A opção de execução silenciosa `-q` possui uma ressalva: encontrar uma correspondência pode resultar em zero mesmo diante de certos erros. Por isso, o contrato e as opções importam. [S30](referencias.md#s30)

“Não encontrei o texto” e “não consegui ler o arquivo” não devem virar a mesma conclusão. Para uma investigação, a ausência de uma observação só é útil quando sabemos que a coleta foi adequada.

Não estamos discutindo ainda a segurança de todo arquivo real. Estamos estabelecendo a disciplina de não transformar uma falha de coleta em evidência de ausência.

## Condições tornam a decisão explícita

Em Bash:

```bash
if printf '%s\n' 'Aurora' > resultado.txt; then
    printf '%s\n' 'escrita concluida'
else
    estado=$?
    printf 'falha de escrita: %s\n' "$estado" >&2
fi
```

`if` usa o status do comando que o segue. `then` inicia o caminho de sucesso; `else` trata o outro caminho; `fi` fecha a construção. O teste automatizado usa uma pasta temporária, não arquivos do leitor.

As listas com `&&` e `||` também usam status. Em `A && B`, B depende do sucesso de A. Em `A || B`, B depende do insucesso de A. O ponto e vírgula apenas separa operações sequenciais: não condiciona a próxima ao sucesso da anterior. [S31](referencias.md#s31)

A sequência `A && B || C` não é uma substituição universal de `if/else`. C também pode executar quando A deu certo, mas B falhou. A intenção precisa sobreviver à leitura do próximo mantenedor, não apenas caber em uma linha.

## A última etapa pode esconder a falha anterior

Este exemplo reproduz o mecanismo da segunda surpresa da Aurora:

```bash
false | true
printf 'pipeline=%s\n' "$?"
```

No Bash sem `pipefail`, o status é zero: vem da última etapa, `true`. A primeira falhou, mas a última terminou com sucesso. O pipeline não examinou o significado de negócio dos resultados. [S23](referencias.md#s23)

Com:

```bash
set -o pipefail
false | true
printf 'pipeline=%s\n' "$?"
```

obtemos um. `pipefail` muda a regra: se existir falha, o status corresponde ao comando mais à direita que retornou valor diferente de zero. Caso todos tenham sucesso, o status é zero. [S32](referencias.md#s32)

Isso ajuda, mas não transforma a cadeia em transação. Uma etapa anterior pode já ter escrito dados. E um produtor pode encerrar com erro porque um consumidor deixou de precisar de mais dados; interpretar isso ainda exige conhecer a cadeia.

O Bash também fornece `PIPESTATUS` para inspecionar os resultados individuais do pipeline anterior. Essa informação deve ser consultada imediatamente: executar outro comando também muda o contexto observado. [S33](referencias.md#s33)

## Por que não basta decorar set -e

É comum encontrar scripts com `set -e` e tratar essa linha como garantia de que “qualquer erro interrompe tudo”. O comportamento possui exceções importantes, incluindo comandos usados em condições e determinadas listas ou pipelines. [S32](referencias.md#s32)

Uma automação precisa definir quais resultados são aceitáveis, como relatá-los e o que fazer com operações parcialmente realizadas. Opções do shell são auxiliares; não substituem esse projeto.

O roteiro didático da próxima seção usa verificações explícitas. A escolha não condena `set -e`: evita apresentar uma opção complexa como uma política completa de tratamento de falhas.

## PowerShell: status, objetos de erro e exceções

No PowerShell, `$?` indica sucesso como um valor booleano. `$LASTEXITCODE` guarda o código do último programa nativo ou script que o definiu. Não são dois nomes para a mesma coisa, e um cmdlet não precisa atualizar `$LASTEXITCODE`. [S34](referencias.md#s34)

Além disso, existem erros que não interrompem toda a execução. Um `try` com `catch` trata erros terminantes; não é correto supor que qualquer mensagem de erro chegará ao `catch` sem considerar o comportamento do comando. O parâmetro `-ErrorAction Stop` pode transformar erros não terminantes de um cmdlet em erros terminantes para aquela chamada. [S35](referencias.md#s35)

Um exemplo de tratamento, para ser lido em PowerShell:

```powershell
try {
    $conteudo = Get-Content -LiteralPath $arquivo -ErrorAction Stop
    # A proxima etapa so usa $conteudo depois dessa leitura.
}
catch {
    throw 'A leitura necessaria para continuar falhou.'
}
```

O caminho é fornecido pelo contexto do exemplo; este bloco não escolhe um arquivo da máquina do leitor. `throw` interrompe aquele caminho com um erro, em vez de fabricar um resultado vazio e tratá-lo como coleta bem-sucedida.

Quando a etapa é um executável nativo, não assumimos que um código diferente de zero virou automaticamente uma exceção. Há políticas e variáveis de preferência que influenciam esse comportamento; conferir o código e a configuração efetiva continua necessário. [S34](referencias.md#s34) [S36](referencias.md#s36)

## Repetição, funções e trabalho em segundo plano

Um laço repete uma operação sobre uma coleção ou enquanto uma condição permitir. Uma função nomeia um conjunto de operações para ser chamado de forma organizada. Nenhum desses mecanismos elimina a necessidade de limitar quantidade, tempo e consequências.

No Bash, iniciar uma operação com `&` pede execução assíncrona. O prompt pode voltar antes do término. `wait` pode aguardar o processo ou job correspondente e obter seu resultado. `jobs`, `fg` e `bg` participam do controle de jobs da sessão. Um job do shell não é um serviço configurado no sistema operacional. [S37](referencias.md#s37)

`Ctrl+C` normalmente envia uma interrupção ao grupo em primeiro plano em um terminal Unix configurado dessa maneira. Não significa “apagar tudo que a execução já fez”. Suspender com `Ctrl+Z` também não equivale a concluir ou desfazer o trabalho. [S37](referencias.md#s37)

O princípio é o mesmo nas duas plataformas: **não confunda uma solicitação de execução, o término de um processo e a confirmação de um resultado**.
