# 14.3 — A tela é só um dos destinos

[← Seção 14.2](14.2-argumentos-aspas-e-expansoes.md) · [Próxima seção →](14.4-status-condicoes-e-controle.md)

Um comando escreve uma informação e ela aparece no terminal. Parece que “escrever na tela” faz parte inseparável de seu trabalho. Mas o mesmo comando pode entregar essa saída a um arquivo ou a outro programa, sem alterar a lógica que produz a informação.

A composição por fluxos é uma das razões pelas quais shells são úteis. Também é uma fonte comum de conclusões erradas quando confundimos tudo que apareceu na janela com um único resultado.

## Entrada, resultado e diagnóstico

No modelo usado pelos exemplos Bash, três descritores possuem papéis convencionais:

| Descritor | Nome | Papel convencional |
| --- | --- | --- |
| 0 | Entrada padrão, `stdin` | Receber dados. |
| 1 | Saída padrão, `stdout` | Entregar resultados. |
| 2 | Saída de erro, `stderr` | Entregar diagnósticos. |

Eles podem estar ligados a um terminal, a arquivos ou a outras interfaces. Não são três variáveis de texto. São referências usadas nas operações de entrada e saída, retomando o que estudamos sobre descritores. [S21](referencias.md#s21)

Escrever em `stderr` não altera automaticamente o código de encerramento do programa. E retornar um erro não obriga o programa a escrever um diagnóstico. Dados, mensagens e status são canais relacionados por um contrato, não pelo fato de serem exibidos perto uns dos outros.

Considere esta função Bash, definida apenas para produzir duas mensagens próprias:

```bash
emitir() {
    printf '%s\n' 'registro'
    printf '%s\n' 'aviso' >&2
}
```

As chaves agrupam o corpo da função. A primeira escrita usa a saída padrão. A segunda redireciona aquela escrita para o descritor 2. Não há erro real sendo provocado; estamos tornando visíveis dois caminhos de saída.

## Redirecionar muda a ligação, não o conteúdo por magia

Em uma pasta descartável dos exemplos:

```bash
emitir > saida.txt 2> diagnostico.txt
```

`saida.txt` recebe `registro` e `diagnostico.txt` recebe `aviso`, cada um com quebra de linha. Os operadores e os nomes usados no redirecionamento são interpretados pelo shell; não viram argumentos normais da função. [S22](referencias.md#s22)

O operador `>` normalmente cria o arquivo ou trunca o arquivo existente antes da execução do comando. `>>` abre para acrescentar. Nenhum dos dois significa “só grave se todo o trabalho der certo”. Um redirecionamento pode modificar um arquivo mesmo quando o comando que viria depois falha. As opções do shell podem alterar a proteção contra sobrescrita. [S22](referencias.md#s22)

Por isso, usar o mesmo arquivo simultaneamente como origem e destino de um redirecionamento destrutivo não é uma técnica de edição segura. E acrescentar com `>>` em uma execução repetida pode duplicar resultados. São consequências do modo de abertura, não defeitos inesperados do disco.

Aqui os testes só criam arquivos temporários próprios. Os nomes apresentados não são um convite para sobrescrever documentos de trabalho.

## A ordem dos redirecionamentos faz diferença

Compare:

```bash
emitir > conjunto.txt 2>&1
emitir 2>&1 > apenas-saida.txt
```

Na primeira linha, a saída padrão passa a apontar para `conjunto.txt`. Depois, o descritor 2 recebe uma cópia dessa ligação. As duas mensagens chegam ao arquivo.

Na segunda, o descritor 2 primeiro copia a ligação anterior da saída padrão. Só depois o descritor 1 é redirecionado para `apenas-saida.txt`. Nesse caso, `aviso` continua seguindo o destino anterior, enquanto `registro` vai para o arquivo. [S22](referencias.md#s22)

`2>&1` não cria uma regra permanente dizendo “acompanhe qualquer futura mudança do 1”. Ele duplica a ligação existente naquele momento.

Essa diferença é importante na coleta de evidências. Um arquivo vazio não prova que a ferramenta ficou silenciosa; a mensagem pode ter seguido outro fluxo.

## Um pipe conecta processos, não mensagens completas

No Bash, `|` conecta a saída padrão de uma etapa à entrada padrão da seguinte. O kernel oferece o mecanismo de **pipe**; os comandos produzem e consomem os dados. Um pipe transporta uma sequência de bytes, não registros de negócio com campos automaticamente conhecidos. [S23](referencias.md#s23) [S24](referencias.md#s24)

Um exemplo pequeno:

```bash
printf '%s\n' 'disponivel' 'emprestado' 'disponivel' |
    grep -F 'disponivel'
```

`printf` produz três linhas. `grep -F` seleciona as que contêm o texto literal informado. A saída tem duas linhas `disponivel`. A correspondência literal é uma escolha explícita; não estamos ensinando ainda toda a linguagem de expressões regulares. [S25](referencias.md#s25)

A saída de erro da primeira etapa não segue automaticamente pelo pipe simples. E o consumidor pode começar a trabalhar antes de o produtor ter terminado tudo. Buffers, limites e encerramentos fazem parte dessa cooperação; não devemos supor que cada escrita do produtor corresponde a uma leitura completa do consumidor. [S24](referencias.md#s24)

Isso retoma o capítulo 10: bytes transportados precisam de um formato. Se uma etapa produzir um aviso no mesmo fluxo em que outra espera registros, a cadeia pode receber algo diferente do combinado.

## O pipeline do PowerShell preserva outra estrutura

Entre cmdlets e funções, o PowerShell pode passar **objetos**, com propriedades e tipos. Uma tabela exibida no terminal é uma apresentação desses dados; não é necessariamente o que a etapa seguinte recebeu. [S26](referencias.md#s26)

Podemos observar isso sem consultar processos ou arquivos da máquina:

```powershell
$livros = @(
    [pscustomobject]@{ Titulo = 'Redes'; Paginas = 120 }
    [pscustomobject]@{ Titulo = 'Sistemas'; Paginas = 240 }
)

$livros |
    Where-Object { $_.Paginas -ge 200 } |
    Select-Object Titulo, Paginas
```

`@(...)` reúne dois objetos. Em cada `@{...}`, associamos nomes a valores; `[pscustomobject]` os transforma em propriedades de um objeto simples. `$_` representa o item sendo processado naquela etapa. `-ge` significa “maior ou igual”. A seleção final conserva o título e a quantidade de páginas do livro `Sistemas`.

Não contamos espaços de uma linha para descobrir onde começa o número. Usamos a propriedade `Paginas`.

Para investigar a estrutura de uma saída, `Get-Member` mostra informações sobre tipos e membros. Para apresentar dados a pessoas, existem comandos como `Format-Table`. Formatar para exibição e selecionar propriedades são decisões distintas: uma etapa que precisa dos objetos originais não deve depender de uma tabela preparada para a tela. [S26](referencias.md#s26) [S27](referencias.md#s27)

## As fronteiras continuam existindo

O PowerShell também usa fluxos separados, incluindo sucesso, erro, aviso, informações detalhadas, depuração e informação. O fluxo de progresso tem tratamento próprio. Não devemos transportar diretamente a tabela de descritores Bash para todos esses fluxos. [S28](referencias.md#s28)

Ao chamar um programa nativo, entram `stdout`, `stderr`, codificação e regras de conversão. A documentação registra mudanças no PowerShell 7.4 para preservar bytes em determinados encadeamentos e redirecionamentos nativos. Isso não torna qualquer pipeline misto um transporte binário transparente. [S28](referencias.md#s28)

A pergunta correta é sempre concreta: **esta etapa entrega texto, bytes ou objetos? O próximo consumidor espera exatamente isso?**

No caso da Aurora, guardar um “relatório” ainda não demonstra que a importação ocorreu. Precisamos descobrir qual etapa o produziu, quais fluxos foram guardados e o que cada etapa sinalizou ao terminar.
