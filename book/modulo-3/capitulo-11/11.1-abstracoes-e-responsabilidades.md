# 11.1 · Um equipamento, muitas promessas

[← Abertura](README.md) · [Próxima seção →](11.2-interfaces-e-chamadas-de-sistema.md)

Na Aurora, uma pessoa consulta o catálogo enquanto outra registra uma devolução. Ao mesmo tempo, um processo prepara uma cópia dos dados e outro espera uma mensagem. Todos usam o mesmo computador, mas nenhum deveria precisar conhecer a disposição física de todos os demais para realizar seu trabalho.

Imagine que cada aplicação pudesse escolher livremente onde escrever na RAM, reprogramar o controlador de armazenamento e impedir qualquer outra de usar a CPU. A convivência dependeria de todos se comportarem bem e de ninguém cometer erros. Uma instrução incorreta poderia transformar o problema de um programa no problema de todos.

O sistema operacional existe, entre outras razões, para que essa convivência não dependa apenas de boa vontade. Ele oferece formas de utilizar recursos, administra sua distribuição e participa da aplicação de limites. Essas responsabilidades cooperam, mas não são a mesma coisa.

## Oferecer uma abstração é esconder detalhes sem apagar regras

A atendente pede ao importador que abra `catalogo.json`. O programa não precisa escolher uma cabeça de disco nem localizar células de um SSD. Ele trabalha com a abstração de arquivo. No Linux, a camada VFS, *Virtual File System*, fornece uma interface comum para diferentes implementações de sistemas de arquivos. [S2](referencias.md#s2)

Uma **abstração** apresenta o que pode ser feito e quais resultados esperar sem exigir que o consumidor administre todos os detalhes internos. Isso não significa que os detalhes deixem de existir. Uma leitura pode depender de dados já presentes em memória, de armazenamento local ou de outros componentes; seu custo e suas falhas continuam ligados ao caminho real.

Podemos comparar com a organização da biblioteca. Quem solicita um título não precisa saber o número de cada prateleira, mas precisa fornecer uma informação que o atendimento consiga interpretar. A organização simplifica o pedido; não garante que qualquer pedido seja válido, permitido ou imediatamente atendido.

No módulo anterior, o processo também apareceu como uma abstração: uma execução possui memória, estado e referências a recursos. A região de memória virtual oferece outra visão organizada. O sistema operacional conecta essas visões a mecanismos concretos, em vez de entregar a cada aplicação controle irrestrito do equipamento.

Por isso, esconder detalhes não é esconder consequências. O contrato precisa permitir distinguir sucesso, ausência, recusa e indisponibilidade. Uma interface que tratasse todos esses resultados como equivalentes tornaria a aplicação mais simples apenas na aparência.

## Administrar um recurso não significa distribuí-lo igualmente

O mesmo computador pode ter capacidade suficiente para atender consultas e produzir uma cópia do acervo. Ainda assim, as duas atividades podem disputar tempo de processamento ou acesso ao armazenamento.

A existência de um administrador não obriga uma divisão igual. Uma organização pode preferir respostas rápidas às consultas durante o expediente e reservar a tarefa mais pesada para outro momento. O sistema fornece mecanismos para expressar prioridades e limites; alguém precisa escolher uma política coerente com o serviço.

Chamaremos de **mecanismo** o meio utilizado para realizar uma decisão, e de **política** o critério que orienta essa decisão. São definições de trabalho para nossa análise. Uma verificação que compara uma identidade com uma permissão é um mecanismo. A regra que concede leitura ao importador e recusa escrita é uma política.

Separar as duas perguntas ajuda a investigar. O mecanismo pode aplicar corretamente uma política inadequada. Também pode haver uma política bem definida que o mecanismo deixa de aplicar em algum caminho. “Existe controle” não diz qual dessas situações encontramos.

## O kernel não é o computador inteiro nem toda a instalação

O **kernel** é o núcleo do sistema operacional: o componente central que administra funções como execução, memória e acesso a recursos protegidos. A instalação que utilizamos inclui ainda bibliotecas, utilitários, serviços, configurações e, eventualmente, uma interface gráfica. A apresentação do Debian distingue o kernel do conjunto de programas que compõe o sistema. [S1](referencias.md#s1)

Usaremos **espaço de usuário**, ou *userspace*, para o ambiente em que executam aplicações e outros componentes fora do kernel. Não é sinônimo de “somente programas sem importância”: um serviço que organiza autenticação ou um gerenciador de serviços pode executar ali e possuir permissões relevantes. A separação entre modo usuário e modo kernel delimita acessos e responsabilidades, não o valor do programa para a organização. [S1](referencias.md#s1)

O terminal e o interpretador de comandos também são programas, não janelas que abrem uma passagem sem regras ao processador. Ao iniciar o importador por um terminal, utilizamos uma interface para solicitar sua execução. Continuamos sujeitos aos mecanismos do sistema.

A área de trabalho é outra forma de interação. Fechar uma janela ou não instalar uma interface gráfica não elimina a necessidade de administrar memória, arquivos e processos. O próprio Debian permite instalações sem ambiente gráfico. [S1](referencias.md#s1)

Uma **distribuição Linux** reúne o kernel Linux com componentes e escolhas de integração: pacotes, ferramentas, configurações e manutenção. Duas distribuições podem compartilhar parte da base e ainda diferir no que instalam ou habilitam. A palavra Linux exige, portanto, contexto: podemos estar falando do kernel ou, informalmente, de um sistema construído ao redor dele.

## Nem todo sistema desenha a fronteira do mesmo modo

No caminho Linux apresentado, subsistemas como o VFS pertencem ao kernel. Isso não estabelece uma divisão obrigatória para qualquer sistema operacional. Há projetos que colocam mais responsabilidades fora do núcleo e organizam a cooperação por comunicação entre componentes. [S2](referencias.md#s2)

Um **microkernel** busca concentrar no núcleo um conjunto reduzido de mecanismos, deixando diversos serviços em componentes externos. O projeto seL4 é um exemplo concreto: sua documentação situa os drivers de dispositivos principalmente em modo usuário, identificando exceções necessárias ao próprio kernel. [S3](referencias.md#s3)

A diferença importa porque a localização de um componente influencia quais dados ele pode alcançar diretamente e como uma falha pode se propagar. Mas o nome da arquitetura não certifica o sistema inteiro. Ainda precisamos examinar permissões, interfaces e configurações. Não vamos transformar uma comparação de organização em uma competição de rótulos.

## O sistema não precisa interpretar cada soma do programa

Quando o importador calcula uma quantidade usando instruções já carregadas, a CPU executa esse trabalho. Não é necessário encaminhar cada soma ao kernel como se o núcleo fosse um interpretador universal.

O kernel participa da preparação, da administração e das transições necessárias ao uso de recursos. Quando a aplicação precisa abrir um arquivo ou obter outro serviço protegido, utiliza uma interface apropriada. A distinção entre as instruções da aplicação e a solicitação ao núcleo será o foco da próxima seção. [S4](referencias.md#s4)

Agora a história inicial ganhou um detalhe: executar o mesmo arquivo não garante receber os mesmos recursos. O sistema operacional não é apenas o cenário onde a aplicação aparece. Ele participa das condições em que ela consegue trabalhar.
