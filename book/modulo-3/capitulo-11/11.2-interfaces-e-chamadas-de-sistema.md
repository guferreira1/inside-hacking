# 11.2 · O pedido atravessa uma fronteira

[← Seção 11.1](11.1-abstracoes-e-responsabilidades.md) · [Próxima seção →](11.3-recursos-espera-e-coordenacao.md)

O importador precisa ler um arquivo. Saber interpretar JSON não lhe entrega os bytes automaticamente: antes disso, algum caminho deve localizar o recurso, decidir se a abertura é possível e fornecer uma referência utilizável.

A **chamada de sistema**, ou *system call*, é uma interface de solicitação de serviços ao kernel. No Linux, ela constitui a fronteira fundamental entre aplicações e o núcleo. Frequentemente uma função de biblioteca prepara essa solicitação e apresenta o resultado ao programa. [S4](referencias.md#s4)

## Um nome no código pode esconder mais de uma etapa

A aplicação pode chamar uma função de alto nível que abre um arquivo e converte seus bytes em texto. Essa função pode usar um runtime, buffers e outras operações antes de entregar o resultado. Não devemos deduzir uma correspondência de uma função para uma única chamada de sistema apenas pela semelhança dos nomes.

Mesmo na biblioteca C, uma função envoltória pode realizar trabalho adicional ou selecionar uma interface do kernel. Já no Python, uma operação de leitura de texto também possui decisões de codificação. A interface do programa e a interface do núcleo pertencem a camadas distintas. [S4](referencias.md#s4) [S6](referencias.md#s6)

Um percurso didático para nossa leitura é:

```text
Aplicação pede os dados
  → biblioteca ou runtime organiza a operação
  → uma interface do kernel é utilizada quando necessária
  → os mecanismos pertinentes tratam o recurso e as condições
  → o resultado retorna à aplicação
  → o programa interpreta os bytes e decide o que fazer com eles
```

O desenho separa responsabilidades. Não pretende listar todas as funções internas nem obrigar toda leitura a alcançar o dispositivo físico. Dados já disponíveis em uma cache podem mudar o caminho de atendimento.

## Entrar no kernel não é receber suas permissões

Para atender uma chamada, a execução pode passar ao modo kernel e depois retornar. Nesse intervalo, o núcleo executa código que implementa o serviço, sob suas próprias verificações. A aplicação não recebe autorização para substituir esse código por instruções arbitrárias com o mesmo nível de acesso. [S1](referencias.md#s1)

Pense na diferença entre solicitar uma operação a um funcionário autorizado e receber a chave da sala onde ele trabalha. A solicitação precisa ser interpretada e pode ser recusada. A analogia deixa de funcionar se imaginarmos que o funcionário confia automaticamente em tudo que foi escrito no pedido.

O mesmo cuidado vale para os argumentos de uma interface. Um endereço fornecido pela aplicação não se torna confiável por ter chegado a uma função do kernel. A implementação precisa respeitar os limites relevantes ao acesso e à operação. A interface `read`, por exemplo, documenta erro quando o buffer fornecido está fora do espaço acessível. [S5](referencias.md#s5)

Essa passagem também não é necessariamente uma troca para outro processo. Podemos atender uma solicitação e voltar ao mesmo fluxo. Uma operação que precise esperar pode permitir outras execuções no intervalo, mas as duas mudanças não são sinônimas.

## Uma abertura estabelece condições para operações seguintes

No Linux, uma abertura bem-sucedida fornece um **descritor de arquivo**. O descritor é utilizado em operações posteriores e se relaciona a uma descrição de arquivo aberto, que conserva estado como posição e modo de acesso. Abrir para leitura não é o mesmo que abrir para leitura e escrita. [S5](referencias.md#s5)

Vamos examinar isso com um exemplo próprio. O programa cria um arquivo temporário com os cinco bytes ASCII de `Livro`. Em seguida, abre esse arquivo apenas para leitura, lê seu conteúdo e tenta escrever um byte usando aquela mesma abertura.

O trecho central da tentativa é este; a preparação e a limpeza estão no arquivo completo:

```python
try:
    os.write(descritor, b"X")
except OSError as erro:
    if erro.errno != errno.EBADF:
        raise
```

`descritor` é a referência obtida anteriormente com `os.open` e `os.O_RDONLY`. `b"X"` representa o byte que tentaríamos gravar. `try` delimita a operação cujo erro será tratado; `except` recebe a exceção comunicada pelo Python. A comparação confere um erro específico, em vez de esconder qualquer problema que aconteça.

O símbolo **EBADF** pode indicar descritor inválido ou abertura incompatível com a operação. Aqui o descritor permanece válido para leitura; ele não foi aberto para escrita. Por isso, interpretar o nome do erro como prova de que o recurso deixou de existir seria incorreto. [S5](referencias.md#s5)

O exemplo também tenta abrir um nome que não foi criado dentro de sua pasta temporária. Nessa operação, recebe **ENOENT**, associado à ausência de componente necessário à resolução do caminho. Não há motivo para tratar essa situação como o mesmo problema da escrita anterior.

## Um resultado executado, com alcance limitado

A execução documentada produziu:

```text
leitura=Livro
fim_da_leitura=0
escrita=EBADF
ausente=ENOENT
conteudo_preservado=sim
```

A segunda linha registra a leitura que não retornou bytes depois de consumir o arquivo regular. Nesse contexto, é fim de arquivo, não uma falha. A última linha confere que o conteúdo permaneceu igual depois da tentativa de escrita.

O [programa completo e suas instruções](exemplos/README.md) são opcionais. Ele não altera permissões de arquivos existentes, não usa credenciais de outras pessoas e não depende de um serviço de rede. A recusa observada decorre do modo da abertura, não de uma demonstração de isolamento entre contas.

Também não houve rastreamento das chamadas de sistema. Observamos os resultados das interfaces utilizadas pelo Python; não contamos transições de modo, leituras físicas ou instruções internas. Essa distinção preserva a utilidade do exemplo sem atribuir a ele medições que não realizou.

## A mensagem de erro é uma pista de uma operação

Nas interfaces C convencionais, muitas funções comunicam falha por um retorno especial e por `errno`; é necessário consultar o contrato da função. O valor de `errno` só deve ser interpretado nas condições em que a função indica erro. O Python normalmente apresenta esses resultados como exceções, conservando informações como o código numérico. [S5](referencias.md#s5) [S6](referencias.md#s6)

Um erro deve ser associado à operação, ao recurso e ao contexto. **EACCES**, por exemplo, aponta para uma recusa de acesso, mas não revela sozinho qual componente do caminho ou qual política ocasionou o problema. O texto traduzido da mensagem também não é um identificador universal entre sistemas.

Na Aurora, “não conseguiu importar” ainda é um relato amplo. O programa falhou ao localizar o caminho, ao abrir o arquivo, ao ler os bytes ou ao interpretar o formato? Preservar essa separação evita tentar corrigir JSON quando a leitura sequer começou.
