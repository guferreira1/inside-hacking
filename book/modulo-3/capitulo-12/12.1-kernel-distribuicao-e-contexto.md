# 12.1 · Linux é o núcleo de qual sistema?

[← Abertura](README.md) · [Próxima seção →](12.2-diretorios-e-montagens.md)

Uma pessoa diz que utiliza Linux. Outra responde que utiliza Debian. Elas podem estar descrevendo a mesma instalação, mas em níveis diferentes.

Linux é o nome do kernel. Debian é uma distribuição que integra esse núcleo a bibliotecas, programas, configurações e um processo de manutenção. O computador que a atendente utiliza resulta dessa composição, não de um único arquivo chamado Linux. A apresentação do Debian distingue expressamente essas peças. [S1](referencias.md#s1)

## Uma história de composição, não de um programa que virou todos os outros

A documentação do kernel atribui a origem do Linux a Linus Torvalds e ao desenvolvimento colaborativo posterior. Descreve um sistema construído segundo a tradição Unix, com interfaces e mecanismos dessa família. Isso não significa que Linux seja uma cópia dos arquivos de um Unix comercial. [S1](referencias.md#s1)

Na composição de sistemas como Debian GNU/Linux, o projeto GNU fornece componentes importantes fora do núcleo. Bibliotecas e utilitários não passam a fazer parte do kernel apenas porque são distribuídos junto dele. O nome GNU/Linux explicita essa combinação; ainda assim, não descreve sozinho todos os componentes de uma instalação. [S1](referencias.md#s1)

A distinção histórica ajuda a interpretar o presente. Não houve um único fabricante escrevendo, de uma vez, o núcleo, o editor, o navegador, o gerenciador de pacotes e cada serviço que utilizamos. Projetos com responsabilidades próprias cooperam por interfaces. Uma distribuição faz escolhas para que esse conjunto possa ser instalado, atualizado e mantido.

Essa composição também explica por que aprender Linux não consiste em reconhecer uma aparência. Podemos trocar a área de trabalho sem trocar o kernel. Podemos usar um serviço sem instalar uma área de trabalho. E podemos encontrar um programa semelhante em instalações que não possuem exatamente as mesmas bibliotecas.

## Distribuição não é apenas tema visual

Imagine duas configurações da Aurora. A primeira inclui o importador, a biblioteca de que ele depende e um gerenciador que o inicia automaticamente. A segunda contém apenas o runtime necessário para executar uma tarefa curta. Ambas utilizam o kernel Linux, mas não fornecem o mesmo conjunto de serviços.

O enunciado “funciona em Linux” precisa, portanto, de condições. O programa foi construído para qual arquitetura? Que interfaces e bibliotecas exige? Como será iniciado? De onde virão sua configuração e seus dados?

O capítulo 8 já mostrou por que compartilhar uma arquitetura de CPU não resolve todas as convenções binárias. Agora acrescentamos a instalação concreta. O nome da distribuição é uma pista para encontrar documentação e pacotes, não uma prova de que toda dependência existe naquele equipamento.

Uma cópia reduzida de uma distribuição pode nem incluir o utilitário que aparece num tutorial. Encontrar “comando não encontrado” não demonstra, por si só, uma incapacidade do kernel: talvez o programa de espaço de usuário simplesmente não tenha sido instalado.

## Identificar o kernel e identificar a instalação são consultas distintas

Duas consultas ajudam a visualizar a separação. O utilitário `uname` informa características do sistema; sua opção `-r` apresenta a identificação da release do kernel em execução. Já `os-release` é um arquivo de identificação da instalação, com campos definidos para esse propósito. [S2](referencias.md#s2)

```sh
uname -r
cat /etc/os-release
```

Essas linhas são consultas opcionais, não uma preparação obrigatória. `cat` apresenta o conteúdo do arquivo indicado. Não fornecemos uma saída universal: o resultado depende do ambiente. A especificação prevê `/usr/lib/os-release` como alternativa quando `/etc/os-release` não existe; não orienta combinar indiscriminadamente os dois arquivos. [S2](referencias.md#s2)

Nesse arquivo, `ID` identifica a distribuição de forma adequada a programas; `PRETTY_NAME` oferece um nome para apresentação. Esses dados não substituem o inventário de cada pacote nem certificam a integridade da instalação. O campo que informa uma identidade é diferente da evidência necessária para confiar em tudo que aquela identidade declara. [S2](referencias.md#s2)

Não precisamos executar o arquivo como um programa para ler sua identificação. Esse cuidado retoma o capítulo 10: interpretar dados de um formato e executar instruções são operações diferentes.

## A visão do processo também entra na identificação

No percurso usual de containers Linux, diferentes conjuntos de arquivos e processos podem utilizar o mesmo kernel, como introduzido no capítulo 11. A organização por namespaces permite separar determinadas visões sem criar, por isso, outro núcleo. [S3](referencias.md#s3)

Assim, ler `os-release` dentro de uma visão de arquivos e consultar o kernel em execução não exige que os resultados descrevam a mesma camada. Não há contradição automática se o arquivo identifica a instalação preparada para a aplicação enquanto o kernel é compartilhado com outro contexto.

Para a Aurora, isso muda nossa investigação. Em vez de anotar somente “Linux”, precisamos registrar de onde a observação foi feita e qual componente ela identifica. O utilitário pode estar correto e ainda responder a uma pergunta diferente da que imaginávamos.

Também não vamos concluir que qualquer diferença prove a presença de um container. O diagnóstico exige mais evidências; versões diferentes entre kernel e pacotes são possíveis por outras razões. A utilidade da distinção é impedir uma conclusão precipitada, não substituí-la por outra.

Temos agora três peças: o núcleo que oferece mecanismos, a instalação que reúne software e a visão concreta do processo que realiza a consulta. A próxima seção examina a organização de nomes que esse processo utiliza para encontrar seus recursos.
