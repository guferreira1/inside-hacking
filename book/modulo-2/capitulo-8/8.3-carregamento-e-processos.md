# 8.3 · Um arquivo ganha um contexto de execução

[← Seção 8.2](8.2-compilacao-e-ligacao.md) · [Próxima seção →](8.4-interpretadores-e-runtimes.md)

O arquivo `catalogo` existe. Enquanto permanece guardado, não está realizando a soma nem apresentando texto. Para participar de uma execução, precisa ser reconhecido pelo ambiente e associado a recursos e estado.

A partir daqui, usaremos **Linux com executáveis ELF** como percurso concreto. Outros sistemas oferecem responsabilidades semelhantes, mas não necessariamente os mesmos formatos, nomes e mecanismos.

## O executável tem organização

**ELF**, *Executable and Linkable Format*, é um formato que pode descrever objetos relocáveis, executáveis e bibliotecas compartilhadas. Seu cabeçalho contém informações como classe, codificação dos dados, arquitetura e tipo. Assim, dois arquivos podem ser ELF e ter papéis diferentes na construção. [S4](referencias.md#s4)

O objeto `principal.o` e o executável `catalogo` ilustram essa diferença. Ambos contêm estruturas reconhecíveis, mas o primeiro ainda participa da ligação; o segundo foi preparado como imagem executável. Nos testes do livro, verificamos esses papéis pelos campos pertinentes, sem inferi-los apenas pela extensão.

**Seções** organizam material usado, por exemplo, na ligação e na análise. **Segmentos** descrevem regiões relevantes para carregar a imagem em memória. Essas visões podem se relacionar, mas não são sinônimos: um segmento pode reunir mais de uma seção. O formato também permite reservar memória cujo tamanho é maior que os bytes correspondentes no arquivo. Não se trata de copiar cada byte do arquivo em fila e começar a executar o primeiro. [S4](referencias.md#s4)

No Windows, a documentação da Microsoft descreve **PE**, *Portable Executable*, e objetos COFF. A palavra “portable” no nome do formato não promete que um executável rode em qualquer sistema. Ainda existe uma arquitetura e um ambiente aos quais aquele artefato se destina. [S5](referencias.md#s5)

## Entender instruções não resolve toda a compatibilidade

A ISA, vista no capítulo anterior, define as instruções da arquitetura. Existe outro conjunto de acordos: a **ABI**, *Application Binary Interface*, ou interface binária de aplicação. Ela estabelece convenções para que componentes binários interajam, como passagem de argumentos, retorno de resultados e uso de registradores.

A documentação de convenções x64 da Microsoft oferece um exemplo concreto dessas regras. Não é necessário memorizar os registradores agora. O que importa é reconhecer que duas funções precisam concordar sobre onde colocar um argumento e onde procurar o resultado. Usar instruções compatíveis com a CPU não basta se os componentes discordam dessas convenções. [S5](referencias.md#s5)

Renomear um arquivo não traduz suas instruções nem adapta sua ABI. Alterar uma permissão também não instala uma biblioteca ausente. São operações que respondem a perguntas diferentes: nome, autorização de acesso, compatibilidade e dependências.

## Programa é uma descrição; processo é uma execução com estado

Um **processo** é uma instância de execução administrada pelo sistema operacional. Ele envolve espaço de endereços, estado de execução e referências a recursos. No Linux, possui um identificador chamado **PID**, *process identifier*. Dois processos podem executar o mesmo programa sem possuir exatamente o mesmo estado. [S6](referencias.md#s6)

Imagine duas pessoas abrindo o mesmo editor para documentos diferentes. O código utilizado pode ser comum, mas o cursor, o texto em edição e os arquivos abertos não precisam ser os mesmos. Não devemos transformar isso numa regra de “uma janela, um processo”: aplicações podem organizar suas instâncias e janelas de maneiras diferentes.

Também não é necessário duplicar fisicamente todas as páginas de código para que existam contextos diferentes. O sistema pode organizar compartilhamentos e cópias segundo suas regras de memória. Para nossa pergunta inicial, basta separar **a imagem do programa** de **cada contexto que a utiliza**. A organização detalhada da memória será o centro do capítulo 9.

## Criar um processo e substituir seu programa são operações distintas

No Linux, `fork` cria um processo filho; `execve` faz um processo existente passar a executar outra imagem de programa. Em uma execução bem-sucedida de `execve`, o PID é preservado, embora a imagem de memória do programa seja substituída. A documentação alerta explicitamente contra descrever `execve` como criação de um processo novo. [S6](referencias.md#s6)

Um caminho possível para iniciar um comando é criar um filho e, nele, executar o programa desejado. Esse percurso permite que o processo que iniciou a operação continue existindo. Não é uma receita obrigatória para todos os sistemas ou lançadores: estamos distinguindo duas responsabilidades que uma interface pode esconder.

Ao receber um pedido de execução, o kernel — a parte central do sistema operacional — verifica condições e prepara a nova imagem. Num ELF dinâmico, o campo pertinente identifica o interpretador de programa, que participa da preparação das bibliotecas. Aqui “interpretador” designa o carregador dinâmico indicado pelo ELF, não um interpretador de Python. [S6](referencias.md#s6) [S7](referencias.md#s7)

## Antes de main, outras instruções já aconteceram

O **ponto de entrada** indicado por um executável não deve ser confundido automaticamente com a função `main`. Existem rotinas de inicialização e, quando necessário, trabalho do carregador dinâmico antes de o corpo principal do programa começar.

A especificação LSB documenta, como exemplo de interface binária, `__libc_start_main`: uma rotina que prepara o ambiente, chama `main` e trata seu retorno. Não é uma declaração de que todas as linguagens ou plataformas utilizam esse nome. É evidência de que a entrada visível ao autor pode vir depois de uma preparação executável. [S8](referencias.md#s8)

No nosso programa, quando `main` solicita a saída, ela utiliza uma biblioteca. Uma chamada de função não é necessariamente uma **chamada de sistema**, ou *system call*: esta é uma interface para solicitar um serviço do kernel. Funções de biblioteca podem realizar trabalho no próprio processo e recorrer ao kernel quando necessário. [S9](referencias.md#s9)

Isso conecta o capítulo ao hardware sem apagar o papel do sistema operacional. A CPU executa instruções, mas o programa comum não precisa comandar diretamente a tela ou o controlador de armazenamento.

O arquivo já ganhou contexto, memória e um caminho de entrada. Falta explicar por que em algumas linguagens não vemos um executável novo aparecer antes de cada execução.
