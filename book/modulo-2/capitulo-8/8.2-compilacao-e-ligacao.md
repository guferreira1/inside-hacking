# 8.2 · Traduzir as peças e encontrar as conexões

[← Seção 8.1](8.1-codigo-e-construcao.md) · [Próxima seção →](8.3-carregamento-e-processos.md)

Imagine que você precisa montar uma equipe. Saber que existe uma função chamada “revisar texto” ajuda a organizar o trabalho, mas não traz automaticamente a pessoa que realizará a revisão. Na construção de programas, reconhecer uma interface e obter sua implementação também são coisas diferentes.

Vamos usar três arquivos. Seus conteúdos completos estão em [exemplos](exemplos/README.md). O primeiro, `acervo.h`, apresenta uma declaração:

```c
int total_exemplares(void);
```

Ela informa o nome, os argumentos e o tipo de retorno da função, mas não contém seu corpo. O arquivo `acervo.c` inclui essa declaração e define o cálculo:

```c
#include "acervo.h"

int total_exemplares(void)
{
    return 2 + 3;
}
```

O terceiro, `principal.c`, utiliza o resultado:

```c
#include <stdio.h>
#include "acervo.h"

int main(void)
{
    printf("Exemplares: %d\n", total_exemplares());
    return 0;
}
```

`main` é o ponto de entrada do programa C no ambiente convencional que usamos, depois da preparação necessária à execução. Não significa a primeira instrução que a máquina inteira executa. Veremos essa diferença na seção 8.3. [S8](referencias.md#s8)

`printf` recebe um formato de saída e o inteiro produzido por nossa função. `%d` indica onde apresentar o inteiro em decimal; `\n` indica uma quebra de linha. Já `return 0` comunica um resultado de encerramento, não a quantidade de exemplares. O programa é propositalmente mínimo e não constitui uma aplicação de produção com tratamento completo de falhas de saída.

## Primeiro, preparar o texto

As linhas iniciadas por `#include` são instruções para o **pré-processador**. Ele insere o conteúdo dos cabeçalhos indicados no material que será traduzido. Um **cabeçalho**, ou *header*, reúne declarações e outras definições compartilhadas. Em nosso caso, `acervo.h` permite que os dois fontes conheçam a mesma declaração. [S2](referencias.md#s2)

Incluir `stdio.h` fornece informações necessárias para usar a interface de saída da biblioteca C. Não significa colar toda a implementação da biblioteca no fonte. Essa confusão faria parecer que o restante da construção já não tem dependências para resolver.

Para observar somente o resultado dessa preparação com GCC, uma opção é:

```sh
gcc -E principal.c -o principal.i
```

`-E` interrompe o processamento depois do pré-processamento; `-o` nomeia o resultado. O arquivo `.i` continua sendo uma representação textual para a etapa seguinte, não a execução do nosso catálogo. As opções são documentadas pelo GCC. [S1](referencias.md#s1)

## Depois, traduzir e montar

Na compilação propriamente dita, a ferramenta analisa a descrição e produz uma representação adequada ao alvo. Uma saída possível é a **linguagem assembly**, que usa nomes textuais para operações e outros elementos vinculados à arquitetura. **Assembly não é o mesmo que código de máquina**: ainda precisa ser convertido para a representação que os componentes seguintes utilizarão.

Podemos pedir ao GCC que pare nessa saída com `-S`. Para produzir um **arquivo objeto** sem realizar a ligação final, usamos `-c`. Estes comandos são janelas separadas sobre o processamento do mesmo fonte; cada um inicia as etapas necessárias a partir do `.c` recebido. [S1](referencias.md#s1)

```sh
gcc -S principal.c -o principal.s
gcc -c principal.c -o principal.o
gcc -c acervo.c -o acervo.o
```

A **montagem**, realizada por um *assembler* ou montador, converte a representação assembly em código objeto. Os comandos acima podem coordenar várias ferramentas sem exigir que você as invoque separadamente.

No nosso exemplo Linux, `principal.o` é um objeto relocável. Ele contém código e informações para sua combinação com outras peças. Ainda há referências a `total_exemplares` e à operação de saída que precisam de tratamento. A presença de instruções de máquina em um arquivo não o torna automaticamente um programa completo pronto para iniciar. [S4](referencias.md#s4)

## Por fim, ligar as referências

Um **símbolo** associa um nome a um elemento usado na construção, como uma função. Resolver uma referência é relacionar seu uso à definição correspondente. **Relocação** envolve ajustar referências de endereço conforme a disposição atribuída às partes. O ligador GNU descreve essas responsabilidades ao combinar objetos e arquivos de biblioteca. [S3](referencias.md#s3)

O **ligador**, ou *linker*, recebe nossas duas peças. Utilizando o GCC como coordenador, podemos solicitar:

```sh
gcc principal.o acervo.o -o catalogo
```

`acervo.o` fornece a implementação da função que `principal.o` utiliza. A configuração convencional do GCC também inclui os elementos de inicialização e a biblioteca C necessários ao exemplo. Não precisamos executar diretamente `ld` nem adivinhar todos esses componentes para acompanhar sua responsabilidade.

O que aconteceria se retirássemos `acervo.o`? A declaração permitiria compilar `principal.c`, mas não forneceria o corpo da função. Na conferência do exemplo, a ligação falhou por falta de definição de `total_exemplares`. A mensagem completa depende das ferramentas; o fato relevante é **qual peça estava faltando e em qual etapa isso se tornou um impedimento**.

Adicionar novamente o cabeçalho não resolveria essa ausência. A interface já era conhecida. Faltava a implementação.

## Nem toda ligação incorpora tudo ao executável

Em uma **ligação estática**, código necessário de bibliotecas pode ser incorporado ao resultado. Em uma **ligação dinâmica**, certas dependências serão atendidas por bibliotecas compartilhadas, com participação do carregador dinâmico. A documentação de `ld.so` descreve como ele encontra, carrega e prepara esses objetos para a execução no Linux. [S7](referencias.md#s7)

Um mesmo programa pode combinar decisões estáticas e dinâmicas. As nossas duas peças locais são combinadas na construção; a configuração convencional pode manter a biblioteca C como dependência compartilhada. Não vamos concluir a composição de qualquer executável apenas pelo comando abreviado: é o artefato produzido que permite verificá-la.

Esse ponto explica por que copiar um arquivo executável pode não transportar tudo de que ele precisa. Também explica por que “compilou” e “conseguiu iniciar nesta máquina” são marcos diferentes.

Temos agora um resultado construído. Mas ainda não explicamos como o sistema reconhece esse arquivo, prepara a memória e entrega a ele uma oportunidade de executar.
