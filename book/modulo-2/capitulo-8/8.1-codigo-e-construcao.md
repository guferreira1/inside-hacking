# 8.1 · O arquivo que você editou não é necessariamente o que executou

[← Abertura](README.md) · [Próxima seção →](8.2-compilacao-e-ligacao.md)

Vamos reduzir o problema da abertura a três objetos. Há um texto que descreve o programa, um arquivo produzido a partir desse texto e uma execução iniciada a partir do arquivo produzido. As três coisas se relacionam, mas não são intercambiáveis.

O **código-fonte** é a representação escrita numa linguagem de programação. Ele também é dado: possui bytes, uma codificação e uma organização. O que o torna código para uma ferramenta é a interpretação segundo as regras da linguagem, não uma propriedade mágica dos caracteres.

Um arquivo contendo uma receita não cozinha um alimento sozinho. Da mesma forma, salvar o texto de um programa não basta para que suas operações ocorram. A analogia termina aí: computadores precisam de regras precisas de tradução e execução, e não de alguém que complete intuitivamente instruções mal formuladas.

## A menor peça útil da nossa história

Este trecho usa a linguagem C e define uma função:

```c
int total_exemplares(void)
{
    return 2 + 3;
}
```

Uma **função** reúne operações que podem ser solicitadas por outra parte do programa. `total_exemplares` é o nome escolhido. O `int` indica que ela devolve um número inteiro; `void`, nessa posição, informa que não recebe argumentos. As chaves delimitam seu corpo, e `return` entrega o resultado a quem a chamou. Aqui esse resultado é cinco.

Não é uma consulta ao catálogo real. Escolhemos números fixos para que a complexidade da aplicação não esconda o processo de construção. A função não imprime nada, não cria arquivos e não altera permissões: somente especifica a devolução de um valor.

No arquivo-fonte, `2`, `+` e `3` são caracteres. O compilador precisa reconhecê-los como partes de uma expressão. A CPU não precisa receber esses três caracteres para efetuar o comportamento correspondente; ela executará instruções da arquitetura para a qual o programa foi preparado.

## Construir é produzir; executar é utilizar

Chamaremos de **construção**, ou *build*, o processo que produz os artefatos necessários a partir das entradas do projeto. Um **artefato** é um resultado concreto desse processo, como um arquivo objeto ou executável. Em um projeto maior, a construção pode envolver mais etapas; nosso exemplo usará a sequência de ferramentas C descrita na próxima seção.

O GCC documenta etapas de pré-processamento, compilação propriamente dita, montagem e ligação. Suas opções permitem interromper o percurso e conservar resultados intermediários. Isso já mostra que o botão “compilar” de uma interface pode esconder várias operações diferentes. [S1](referencias.md#s1)

Agora suponha que construímos `catalogo` a partir da função que devolve cinco. Depois alteramos apenas o fonte para `return 2 + 7;`. O executável anterior não foi reescrito por essa edição. Iniciá-lo novamente ainda utiliza o artefato anterior, que apresenta cinco. Para que a mudança entre em um novo executável, precisamos reconstruí-lo e iniciar essa nova versão.

Esse comportamento foi conferido nos exemplos do livro: editar o fonte preserva a saída do executável já produzido; reconstruir o exemplo alterado muda a saída para nove. Não é uma regra sobre ferramentas com reconstrução automática. Se uma ferramenta observa os arquivos e refaz a aplicação, é ela que acrescenta essa etapa ao processo.

A diferença importa numa investigação. Ler o código de uma versão não demonstra que o serviço em execução foi construído a partir dela. Se a versão examinada e a versão executada não coincidem, podemos procurar uma causa no lugar errado.

## Traduzir não é trocar cada palavra por uma instrução

Um compilador não precisa gerar uma instrução de máquina para cada linha. A quantidade de linhas depende até de como o autor distribuiu espaços e quebras. Uma expressão pode exigir várias operações; outra pode ser simplificada durante a tradução.

Por exemplo, o cálculo fixo `2 + 3` pode ser resolvido antes da execução, de modo que o código produzido trabalhe diretamente com cinco. Opções de otimização do GCC controlam diferentes transformações, dependentes do alvo e da configuração. Não vamos presumir uma sequência particular de instruções nem um ganho de velocidade sem examinar o resultado. [S14](referencias.md#s14)

Isso explica uma dificuldade futura da engenharia reversa. Mesmo que consigamos ler instruções do binário, não devemos esperar recuperar cada nome, comentário ou escolha de formatação do fonte. A construção transforma a representação; não guarda obrigatoriamente todas as informações usadas para produzi-la.

Também não confundiremos compilação com uma prova de segurança. Uma ferramenta pode aceitar um programa que calcula o número errado ou que permite uma ação indevida. Reconhecer uma descrição válida para a linguagem é uma pergunta; comprovar que ela atende às regras da aplicação é outra.

## O que a próxima etapa precisa receber?

Nossa pequena função devolve um valor, mas ainda não contamos como exibi-lo. Precisaremos de outra função que a chame e de uma operação de saída. Essa separação é intencional: tornará visível a diferença entre reconhecer o nome de uma operação e encontrar sua implementação.

Na próxima seção, vamos acompanhar as peças até que elas formem um executável. A pergunta deixa de ser “qual comando faz aparecer um arquivo?” e passa a ser **“o que cada transformação acrescenta e o que ainda falta depois dela?”**
