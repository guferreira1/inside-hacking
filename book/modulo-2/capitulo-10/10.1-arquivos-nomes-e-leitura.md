# 10.1 · O nome aponta; os bytes contam outra parte

[← Abertura](README.md) · [Próxima seção →](10.2-formatos-e-estrutura.md)

A Aurora guarda uma exportação em `exportacoes/livro.json`. Para quem usa um gerenciador de arquivos, o documento parece ser seu nome e seu ícone. Para o programa que o abre, há uma sequência de operações: resolver o caminho, obter acesso a um objeto e ler conteúdo por uma interface.

Chamaremos de **arquivo regular** o tipo de arquivo que utilizamos aqui para guardar uma sequência de bytes. O sistema de arquivos também pode apresentar diretórios, links e outros tipos de objeto. Não vamos confundir essa classificação com formatos de conteúdo: um JSON e uma imagem PNG podem ser ambos arquivos regulares. [S1](referencias.md#s1)

## Caminho não é conteúdo

Um **caminho**, ou *pathname*, é uma expressão usada para localizar um objeto na organização de nomes do sistema. O caminho relativo da abertura depende de uma base, como o diretório de trabalho visto no capítulo 8. Os bytes do título e da quantidade não estão contidos no nome `livro.json` só porque ele os descreve bem.

Vamos construir duas situações. Na primeira, copiamos o conteúdo para outro arquivo. Na segunda, criamos outro nome para o mesmo objeto. Uma comparação dos bytes pode inicialmente produzir igualdade nos dois casos. Mas alterar uma cópia não tem necessariamente o mesmo efeito que alterar o objeto alcançado por dois nomes.

No modelo Linux, um **inode** mantém metadados associados ao arquivo. Um **hard link**, ou ligação física, acrescenta uma referência ao mesmo objeto no sistema de arquivos. Não cria uma segunda cópia de seu conteúdo. Um **link simbólico** guarda um caminho que será interpretado para alcançar outro destino. Ele pode continuar existindo mesmo quando esse destino já não existe. [S1](referencias.md#s1)

Por isso, um link não é automaticamente uma cópia de segurança. Se dois nomes alcançam os mesmos dados, a alteração desses dados poderá ser vista pelos dois. E um número de inode só tem significado dentro de seu sistema de arquivos; não é uma identidade universal e eterna para qualquer documento.

## Abrir estabelece uma referência de trabalho

Ao abrir um arquivo no Linux, o processo recebe um **descritor de arquivo**, conceito introduzido no capítulo 8. Esse número se relaciona a uma descrição de arquivo aberto, que acompanha estado como posição de leitura e modo de acesso. O descritor não é simplesmente o texto do caminho guardado para repetir a busca a cada byte. [S1](referencias.md#s1)

Isso permite um comportamento que parece estranho à primeira vista: remover um nome não precisa invalidar um arquivo que um processo já mantém aberto. No Linux, se o último nome for removido enquanto o arquivo continua aberto, seu conteúdo permanece disponível por aquela abertura até que as referências pertinentes sejam liberadas. Isso não é um procedimento de recuperação forense: é a semântica documentada de remoção de nomes e arquivos abertos. [S1](referencias.md#s1)

Conferimos um caso pequeno nos testes do livro. Criamos um arquivo temporário com os bytes de `Livro`, acrescentamos um segundo nome por hard link, abrimos o arquivo e removemos os dois nomes. A leitura pela abertura existente ainda devolveu `Livro`. O teste só utilizou objetos que ele próprio criou.

O resultado separa três coisas que antes pareciam uma só: **nome disponível, objeto aberto e conteúdo acessível por aquela referência**. Ele não demonstra que qualquer arquivo excluído possa ser recuperado depois de fechado.

## Metadados também precisam de contexto

**Metadados** são informações sobre o objeto: tipo, tamanho, proprietário, permissões e marcas de tempo são exemplos. Alguns pertencem ao sistema de arquivos; outros podem estar dentro do próprio formato do documento.

Não transforme uma palavra familiar em uma interpretação automática. No Linux, `mtime` indica modificação de conteúdo, enquanto `ctime` indica mudança de estado do inode; este último não é simplesmente “data de criação”. Marcas de tempo têm regras de atualização próprias. [S1](referencias.md#s1)

A Aurora pode ainda guardar dentro do JSON um campo chamado `data_exportacao`. Esse campo foi escrito pela aplicação. Ele não é a mesma medida que a marca de tempo do sistema de arquivos e não se torna verdadeiro por receber um nome convincente.

Essa distinção importa numa investigação: se queremos saber quando um conteúdo foi produzido, não podemos escolher uma data qualquer na tela sem identificar quem a gerou e o que ela registra.

## Ler é receber uma quantidade de bytes

Um programa mantém um **offset**, deslocamento em relação ao início de uma sequência. Num arquivo regular aberto para leitura, esse estado ajuda a indicar de onde virá a próxima porção.

Considere os cinco bytes de `Livro` em ASCII. Uma leitura dos dois primeiros entrega `Li`; uma leitura posterior, a partir da posição dois, encontra `vro`. Nenhum separador invisível foi inserido entre as partes. Fomos nós que dividimos o trabalho de leitura.

Na interface `read` do Linux, solicitar uma quantidade significa tentar receber até aquela quantidade. Uma resposta menor pode ser normal, e o programa deve examinar quantos bytes realmente chegaram. Com uma solicitação de tamanho positivo, chegar ao fim de um arquivo regular pode produzir retorno zero. **EOF**, *end of file*, é essa condição de fim no percurso considerado, não um byte obrigatório escondido depois do último caractere. [S2](referencias.md#s2)

Bibliotecas podem oferecer operações de nível mais alto e lidar internamente com várias leituras. Ainda assim, um leitor de formato precisa distinguir “pedi oito bytes” de “recebi os oito bytes necessários ao cabeçalho”. Um arquivo truncado não se completa porque a chamada solicitou o tamanho certo.

## Os bytes não precisam formar uma frase

Abrir em modo binário permite trabalhar com bytes. Abrir em modo texto acrescenta interpretação de codificação e pode transformar finais de linha. Na biblioteca `io` de Python, essas são interfaces com comportamentos distintos. [S2](referencias.md#s2)

Nos testes, a sequência `41 0D 0A 42 0A`, cinco bytes, foi lida como `A`, quebra de linha, `B`, quebra de linha em uma configuração de texto que normaliza finais de linha. A apresentação não preservou uma correspondência de um caractere visível para cada byte original.

Isso não torna a leitura textual errada. Torna necessário escolher a interface conforme a pergunta. Para contar bytes de um formato, usamos o conteúdo binário. Para interpretar texto, declaramos a codificação e as transformações permitidas.
