# 10.3 · Transformar a escrita não transforma tudo na mesma coisa

[← Seção 10.2](10.2-formatos-e-estrutura.md) · [Próxima seção →](10.4-serializacao-e-contratos.md)

A exportação precisa atravessar um canal que aceita texto, mas nosso registro AUR contém campos numéricos binários. Podemos representar os bytes usando caracteres adequados ao canal. Isso resolve uma questão de transporte, não transforma o registro em segredo.

É nesse ponto que palavras como codificar, escapar, comprimir e criptografar costumam se misturar. Vamos acompanhar o que cada operação faz com o conteúdo.

## Texto e bytes continuam sendo camadas diferentes

No capítulo 6, `é` precomposto virou `C3 A9` em UTF-8. Codificar texto é escolher a sequência de bytes correspondente àquela representação. Decodificar faz o percurso de interpretação dos bytes para o texto, respeitando as regras de validade. UTF-8 não aceita qualquer sequência arbitrária como um caractere completo. [S6](referencias.md#s6)

Se um arquivo contém o byte `FF` isolado onde deveria existir UTF-8, substituir silenciosamente o problema por um símbolo visível altera a informação. Essa substituição pode ser útil numa visualização tolerante; não é a mesma política que validar um registro para importação.

Nosso leitor AUR rejeita título com codificação inválida. Assim, uma tentativa de ler não se transforma, sem aviso, numa operação de conserto. Para uma ferramenta de investigação, preservar o conteúdo original e registrar um erro pode ser mais útil do que fabricar um texto aparentemente normal.

## Base64: representar bytes num alfabeto textual

**Base64** agrupa bits e os representa por caracteres de um alfabeto de 64 posições. Na forma com preenchimento definida pela RFC 4648, grupos de três bytes, ou 24 bits, tornam-se quatro caracteres de seis bits cada. O sinal `=` participa do preenchimento quando o último grupo é incompleto. [S7](referencias.md#s7)

Veja a transformação de três bytes conhecidos:

```text
Bytes de ABC: 01000001 01000010 01000011
Grupos:       010000   010100   001001   000011
Valores:         16       20        9        3
Base64:           Q        U        J        D
```

A saída é `QUJD`. Usando o alfabeto e a regra inversa, recuperamos os bytes de `ABC`. Nenhum segredo foi necessário.

Nosso outro exemplo, os cinco bytes de `Livro`, torna-se `TGl2cm8=`. São oito caracteres ASCII, em vez dos cinco bytes originais. Para n bytes, a forma com preenchimento ocupa `4 × teto(n / 3)` caracteres, sem contar quebras de linha ou invólucros adicionais. Teto significa arredondar para cima até o próximo inteiro.

Essa expansão explica por que Base64 não é compressão. Também não é criptografia: serve para representar bytes, não para exigir uma chave de acesso. A variante **Base64url** modifica parte do alfabeto; o tratamento de preenchimento depende do protocolo que a utiliza. As variantes não devem ser misturadas por adivinhação. [S7](referencias.md#s7)

Na implementação do livro, as conversões foram verificadas com a biblioteca `base64` do Python. A opção de validação utilizada no teste ajuda a rejeitar caracteres fora do alfabeto aceito; não valida o formato interno dos bytes recuperados. [S7](referencias.md#s7)

## Escape responde à gramática do lugar

Um **escape** permite representar conteúdo que tem significado especial numa sintaxe. Em uma string JSON, por exemplo, `\n` pode representar uma quebra de linha sem inserir literalmente aquela quebra entre aspas. As regras são da gramática JSON, não de todos os formatos textuais. [S10](referencias.md#s10)

Já a **codificação percentual** de URIs utiliza `%` seguido de dois algarismos hexadecimais para representar um octeto. Ela tem condições próprias sobre caracteres reservados e componentes de uma URI. Uma transformação apropriada para um componente não é uma limpeza universal de qualquer texto. [S8](referencias.md#s8)

Uma experiência pequena revela a importância de contar camadas. Partimos do texto `A%2520B`. Uma decodificação percentual produz `A%20B`, porque `%25` representa o próprio sinal de porcentagem. Uma segunda produz `A B`.

Esses resultados foram conferidos nos testes com dados constantes. A primeira e a segunda operação não são equivalentes. Se uma etapa examina a primeira representação e outra aplica uma transformação adicional antes de usar o valor, elas já não estão decidindo sobre o mesmo texto.

Isso não significa que a solução seja decodificar repetidamente até a aparência parar de mudar. O contrato precisa determinar quantas camadas existem e em que ordem interpretá-las. Uma sequência escrita para representar literalmente `%20` não deve virar um espaço por iniciativa de um componente que inventou uma camada extra.

## Normalizar não é remover acentos

Retomemos as duas representações de `é`: um ponto de código precomposto ou `e` seguido de acento combinante. Elas podem representar a mesma letra sem possuir os mesmos bytes.

**Normalização Unicode** aplica regras para lidar com classes definidas de equivalência. NFC e NFD tratam equivalência canônica; NFKC e NFKD incluem transformações de compatibilidade que podem eliminar distinções relevantes. A escolha depende da finalidade do texto. [S9](referencias.md#s9)

Conferimos que NFC torna iguais as duas representações específicas de `é` do nosso exemplo. Isso não significa tornar qualquer nome visualmente parecido igual, retirar acentos ou resolver toda comparação de identificadores.

Imagine que a Aurora decida preservar títulos exatamente como recebidos para reproduzir um documento original. Outra funcionalidade pode querer comparar títulos segundo uma convenção normalizada. São objetivos diferentes. É possível manter o original e produzir uma forma de comparação explicitamente definida, em vez de substituir uma coisa pela outra sem registro.

Também precisamos separar normalização textual de **canonicalização de um documento**. Esta pode definir ordem de campos, escrita de números e espaços além das strings. O esquema JCS para JSON, por exemplo, não determina normalização Unicode das strings: preserva seus dados conforme o contrato da especificação. [S16](referencias.md#s16)

O fio condutor é perguntar **o que foi transformado, segundo qual regra e para qual uso**. Conhecer o nome “codificação” sem identificar a camada não basta.
