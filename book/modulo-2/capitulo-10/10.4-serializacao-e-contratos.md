# 10.4 · Levar uma estrutura para fora do processo

[← Seção 10.3](10.3-codificacoes-e-transformacoes.md) · [Próxima seção →](10.5-parsing-e-validacao.md)

Dentro de um processo, o programa da Aurora mantém um registro com título e quantidade. Para gravá-lo ou entregá-lo a outro componente, precisa escolher uma representação que esse componente consiga reconstruir.

Chamaremos de **serialização** a transformação de uma estrutura de dados numa representação transportável ou armazenável. **Desserialização** é a reconstrução de valores ou estruturas a partir dessa representação, conforme um formato e uma implementação.

Nosso AUR já realiza essa tarefa. Ele transforma um registro em campos binários. A mesma informação pode também ser representada em JSON:

```json
{"titulo":"Livro","quantidade":3}
```

Não são os mesmos bytes do AUR, mas nosso contrato permite reconstruir o mesmo título e a mesma quantidade a partir dos dois.

## Não é uma fotografia da memória do processo

O registro pode conter referências internas que fazem sentido apenas na execução atual. Copiar um número de endereço não leva consigo o objeto que ele alcançava no capítulo 9.

Por isso, serializar não significa obrigatoriamente despejar a RAM no arquivo. Definimos quais valores devem atravessar a fronteira e como representar suas relações. Outra execução pode reconstruí-los em endereços completamente diferentes.

A questão fica concreta se acrescentarmos ao objeto da Aurora uma conexão aberta com um serviço. Guardar o número local que identifica essa conexão não obriga o destinatário a receber uma conexão equivalente. Para transmitir a intenção “consultar o serviço”, seriam necessárias outras informações e uma operação autorizada, não apenas a cópia de um identificador interno.

## JSON dá estrutura; a aplicação dá o contrato dos campos

**JSON**, *JavaScript Object Notation*, oferece objetos, arrays, strings, números e os valores `true`, `false` e `null`. Um objeto reúne nomes e valores; um array organiza uma sequência. JSON é um formato textual de dados, não um pedido para executar um programa JavaScript. [S10](referencias.md#s10)

No registro da abertura, `titulo` identifica uma string, e `quantidade` identifica um número. Estas três entradas, porém, não são equivalentes:

```json
{"quantidade":3}
{"quantidade":"3"}
{"quantidade":null}
```

A primeira contém um número, a segunda contém texto e a terceira indica `null`. Também é diferente omitir o campo. O programa precisa decidir quais dessas situações fazem sentido; o nome do formato não toma essa decisão por ele.

Um **esquema**, ou *schema*, descreve a estrutura esperada, os tipos, os campos e suas restrições. Nosso perfil didático exige exatamente `titulo` e `quantidade`, sem nomes adicionais; título com 1 a 80 bytes UTF-8 e quantidade inteira de 0 a 1000. No leitor Python que acompanha o capítulo, quantidades escritas com fração ou expoente são rejeitadas, mesmo que seu valor matemático pudesse ser inteiro. Essa restrição é nossa, não uma regra geral de JSON.

## Dois nomes iguais criam uma decisão que não podemos esconder

Considere agora:

```json
{"titulo":"Livro","quantidade":3,"quantidade":7}
```

Qual quantidade deve prevalecer? A RFC 8259 recomenda nomes únicos e alerta para diferenças de comportamento quando eles se repetem. Não define esse caso como um acordo universal em que todos escolherão necessariamente o primeiro ou o último valor. [S10](referencias.md#s10)

A implementação padrão de `json.loads` do Python conserva o último valor para um nome repetido. No nosso exemplo, isso produz sete. Já o perfil da Aurora rejeita a duplicação usando uma verificação durante a construção do objeto. Ambos os comportamentos foram conferidos nos testes; não estamos descrevendo uma falha encontrada num serviço real. [S11](referencias.md#s11)

Por que rejeitar nesse contrato? Porque o emissor deve produzir uma quantidade única. Escolher silenciosamente uma das duas esconderia uma ambiguidade que outra etapa poderia resolver de maneira diferente.

Também não basta procurar o mesmo trecho de texto duas vezes. Um nome JSON pode conter escapes que, depois de interpretados, resultam no mesmo nome. A verificação deve operar no nível em que os nomes já foram reconhecidos pela gramática.

## CSV: uma vírgula pode ser conteúdo

**CSV**, *Comma-Separated Values*, organiza registros e campos textuais. O formato comum documentado pela RFC 4180 permite delimitar com aspas campos que contêm vírgulas, aspas ou quebras de linha. Existem variantes; delimitador, codificação e outras convenções precisam ser combinados. [S12](referencias.md#s12)

Nossa exportação poderia conter:

```csv
titulo,quantidade
"Redes, sistemas",3
```

Na segunda linha, `Redes, sistemas` é um único título. Dividir o texto simplesmente em cada vírgula produziria três pedaços, não dois campos. Um leitor CSV reconhece a função das aspas antes de decidir onde termina cada campo.

Na conferência com `csv.reader`, o título foi reconstruído como um campo e a quantidade chegou como texto `3`. Interpretar esse campo como inteiro e verificar seu limite é outra etapa. O formato tabular não fornece sozinho os tipos do nosso domínio. [S12](referencias.md#s12)

## Outros formatos fazem escolhas diferentes

**XML**, *Extensible Markup Language*, representa estruturas com elementos e atributos. Possui regras de boa formação e mecanismos adicionais de validação; reconhecer uma árvore bem formada não resolve todas as regras do domínio. [S13](referencias.md#s13)

**YAML**, *YAML Ain’t Markup Language*, oferece uma representação textual com mapeamentos, sequências e valores. A resolução de certos valores depende do esquema e da versão adotados. A especificação 1.2.2 distingue esses mecanismos; não é adequado tratar toda aparência de texto sem aspas como uma string invariável. [S13](referencias.md#s13)

**Protocol Buffers**, ou Protobuf, utiliza uma representação binária estruturada por números de campo e tipos de transporte. O esquema relaciona essas marcações ao significado dos campos. Encontrar um número de campo não revela sozinho seu nome ou a regra de negócio que o originou. [S14](referencias.md#s14)

Esses contrastes não são uma disputa para escolher um formato universalmente superior. CSV pode ser conveniente para dados tabulares; um esquema binário pode facilitar outro tipo de integração. A escolha precisa considerar tipos, evolução, interoperabilidade, ferramentas e limites de processamento.

No AUR v1, rejeitar uma versão desconhecida é a regra explícita. Num formato que prevê evolução por campos, pode haver uma regra documentada para reconhecer ou ignorar extensões. **Compatibilidade não significa aceitar qualquer conteúdo: significa preservar um acordo definido entre versões.**
